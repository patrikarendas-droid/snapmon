browser game gets no releases and no feature parity, and Android features never need a Chrome fallback. The shared
JavaScript in `src/` stays: the app's WebView runs it, and the developer catalogue uses part of it. Rollback, backups
and long-term APK archives: [`docs/RECOVERY.md`](RECOVERY.md). **Primary owner-verified build: 22** (commit `0681beb`,

## What the app changes compared with the website (and what it does not)

Same files, same game: `src/` is shared. The game logic, odds, battle maths, objects, curated writing, sprites and the
recognition rules are not modified for Android. Platform-only differences:

- `src/platform.js`: when the boot script sets `window.SNAPMON_NATIVE`, storage writes are also mirrored to native
  files, `Platform.assets.bundled` is true, and the camera-permission/unsupported texts point to Android settings
  instead of a browser address bar. Without `SNAPMON_NATIVE` (the website) it behaves exactly as before
  (`tests/android-packaging.js` checks this).
- Bundled engine (`Platform.assets.bundled`): no "one-time download" notice, the engine starts at app launch, the
  detector/classifier are read straight from the APK and TinyCLIP's files are not copied a second time into the
  browser cache (they are still size- and SHA-256-checked against `models/manifest.json` on every load). The
  developer-only "TinyCLIP on GPU" comparison is unavailable (its 22 MB WebGPU runtime is not packaged).
- Settings shows the Android build ("Android app 0.6.0-dev.N+sha · DEVELOPMENT BUILD") and an "Open-source
  licences" sheet (`THIRD_PARTY_NOTICES.md`, packaged).
- Packaging only (`tools/android/build-web.js`): TF.js weight shards are renamed `group1-shardNofM` → `….bin` and
  their `model.json` paths updated, because Capacitor's local server cannot serve a file without `.` in its name (it
  returns `index.html` with html5mode, nothing without); the weight bytes are unchanged and SHA-256-checked. No developer catalogue, no `dist/`, no PWA manifest; fonts bundled
  (no Google Fonts); `env(safe-area-inset-*)` also reads Capacitor's `--safe-area-inset-*` (older WebViews report 0
  in edge-to-edge apps); game scripts are started by `native/boot.js` after saves are restored.

Known wording limitation: a few Settings texts still say "in this browser" (they are correct on the website).

**Layout with system bars (fixed after the owner's phone test of build 9).** With Android System WebView ≥ 140 (the
owner's phone) Capacitor 8 draws the page under Android's status and navigation bars and reports their sizes as
`--safe-area-inset-*` (CSS px); with an older WebView it pads the WebView below the bars instead (insets 0) — that is
why the CI emulator (WebView 113) could not show the bug, and why its layout test also emulates the phone's insets. The sticky HUD (`.topbar`, `top: env(safe-area-inset-top)`) was offset by the status
bar height while nothing reserved that space, so at scroll 0 the HUD was pushed down over the top of every screen
(Gear's Arsenal / Bag / Shop & Craft could not be tapped). Fix in the shared CSS: `#app` has
`padding-top: env(safe-area-inset-top)` (the HUD's normal position now equals its sticky offset), and sheets are capped
below the status bar. Both are exactly 0 in a browser tab, so the website is unchanged. Guarded by
`tests/e2e-layout.js` (Chromium: 3 sizes × 4 inset sets × 11 screens; fails on the old CSS with the phone's symptoms)
and the emulator test (same checks in the real WebView with the real system bars + a real `adb` tap on Shop & Craft).

## Saves in the Android app

- **Separate from Chrome.** The app runs at its own origin (`https://localhost` inside the APK). It never reads the
  website's localStorage, backup codes or anything else, and the website never sees the app's data. There is no
  automatic migration in either direction. The Chrome saves are not touched.
- **Clean start.** A fresh install has no data, so the game creates the normal brand-new-player state.
  `allowBackup="false"` + `data_extraction_rules.xml` stop Android from restoring old app data from Google backup or a
  previous phone, so a reinstall also starts clean.
- **Two copies, newest wins.** The game saves synchronously to the WebView's localStorage as before
  (`Platform.storage`). Every write is also queued to the `SnapmonSaveStore` plugin, which writes one file per key in
  the app's private `files/snapmon-store/` using Android's `AtomicFile` (write → fsync → rename: an interrupted write
  leaves the old or the new save, never a broken one). Each write carries a revision number. At start-up
  (`native/boot.js`), before any game script runs, the files are read and the newer copy of each key wins; values only
  localStorage has are copied to the files. So neither a lost WebView storage nor a failed file write rolls progress
  back. Failed file writes are counted and shown in Settings.
- **Before the app closes:** the game already saves immediately when the app is hidden; the boot script also saves on
  Android's `pause` event, and double-Back exit waits (up to 4 s) until queued file writes are on disk.
- **Updates keep the data** (same package + same signing key + higher versionCode; see "Signing"). Uninstalling, or
  Android Settings → Apps → SnapMon Dev → Storage → Clear storage, deletes it. **Export a backup code first**
  (Settings → Back up your progress; keep two private copies, `docs/RECOVERY.md`). Deleted/expired Actions artifacts,
  releases or branches never touch the installed app's data.
- The save format is unchanged (format 3), so app saves and website saves remain mutually compatible via backup codes.

## Building the APK (GitHub Actions)

`.github/workflows/android-apk.yml` (needs no local Android tools):
1. **tests**: the website's full regression suite (`tools/android/run-tests.sh`: every test of `pages.yml`, plus
   `tests/android-packaging.js`).
2. **apk**: TinyCLIP export (same command and cache key as Pages) → `tools/android/fetch-engine.sh` (detector,
   classifier, TF.js 4.22.0, ONNX Runtime Web 1.20.1 — the same pinned versions as Pages) → `npm ci` →
   `build-web.js --dev-tools` + `check-web.js` (every engine file present, every SHA-256 matches the manifest, nothing
   loads from the network, no catalogue) → `tests/e2e-android-web.js` with the **real** engine in Chromium →
   `npx cap sync` → signing key from the secret → `./gradlew assembleDebug` → APK checks (package, versionCode, only
   CAMERA, engine files inside, no catalogue, signature) → update-test builds (versionCode + 1 and + 3, current code)
   and a **recovery-drill** build (the commit in `tools/android/recovery-points.json` → `drill`, versionCode + 2, same
   key) → artifact **SnapMon-Dev-APK-…** (the APK + `provenance.json` + `SHA256SUMS`, **kept 90 days**) + a summary.
3. **emulator**: Android 14 emulator (x86_64) runs `tools/android/emulator-smoke.js` against the built APK, including
   the recovery drill (see Tests).

**Finding and identifying an APK.** The *Build the debug APK* job's summary starts with "SnapMon Dev APK — download
this": a **direct link** to the artifact, the file name, the expected expiry date, run number and attempt, source
commit, versionName/versionCode, APK SHA-256, artifact-zip SHA-256 and the certificate fingerprint. The same values are
in `provenance.json` inside the zip and in the job log. Artifact names: `SnapMon-Dev-APK-<game>-build-<run>`; if that
job itself is re-run, the new binary is named `…-attemptN` (same versionCode — install only one of them). A red
*emulator* job with a green *Build the debug APK* job means the APK was built and verified but the emulator test failed
(often a CI emulator boot flake): **Re-run failed jobs** re-tests the same APK without rebuilding it.

**Retention.** The main APK artifact is kept **90 days** (`retention-days: 90`, the maximum GitHub allows for a public
repository; verified on the artifact's `expires_at` after the first build with it). Diagnostics are short: update-test
APKs 3 days, screenshots 7 days. This applies to new uploads only: older artifacts keep the expiry they were uploaded
with (builds ≤ 14: 30 days; build 14 expires 2026-12-24). An artifact expiring has **no effect** on the installed app
or its saves. Builds worth keeping longer: owner-approved milestone pre-releases (`docs/RECOVERY.md`). If a repository
setting ever caps it: GitHub → the repository → **Settings → Actions → General → Artifact and log retention** → 90 →
Save (the summary's expiry date then shows the real value).

Triggers: every push to `feature/android-**` (and this first session's branch `ccr-6eaf78d0-vj87lh`) that touches the
game or the app, and **Run workflow** (that button appears in the Actions tab only once the workflow file is on the
default branch, i.e. after a merge into production). Any finished run can also be repeated with **Re-run all jobs**.
Versions: `versionCode = 1000 + run number` (grows with every run), `versionName = <GAME_VERSION>-dev.<run>+<sha>`.
Android refuses to install a lower versionCode over a higher one: always install the newest build.

Local build (optional; needs JDK 21 + Android SDK 36): `tools/android/fetch-engine.sh /tmp/engine` (after exporting
TinyCLIP as in `pages.yml`) → `cd android-app && npm ci` → `node ../tools/android/build-web.js --engine /tmp/engine
--dev-tools` → `npx cap sync android` → `cd android && ./gradlew assembleDebug`.

## Signing (one-time action by the owner)

Android installs an update only if it is signed with the **same certificate** as the installed app. A CI runner's
default debug key is new on every run, so without a stable key each new APK would refuse to update the old one, and
the only way forward (uninstall) would delete the saves.

**One-time setup (from the phone):** GitHub → the repository → Settings → Secrets and variables → Actions → New
repository secret → Name `ANDROID_DEV_SIGNING_SEED`, Secret: a long random passphrase (at least 24 characters; e.g.
generated by your password manager; keep a copy there). Save. Then re-run the workflow.

- `tools/android/dev-keystore.py` derives the RSA-2048 key and a self-signed certificate (valid 2026–2076)
  deterministically from that passphrase inside the CI job; the same passphrase always gives the same certificate.
  The keystore exists only during the job and is deleted afterwards. No key file is committed or uploaded.
- The run summary prints the certificate's SHA-256 fingerprint: it must stay the same from build to build. Verified
  locally: two independently generated keystores from one passphrase produced byte-identical certificates and APKs
  signed with v2 + v3 schemes.
- Without the secret the workflow still builds, but names the artifact `…-UNSTABLE-SIGNING` and warns: such an APK
  cannot be updated by a later build. If you installed one, uninstall it before installing a stable-signed build (an
  unstable build has no saves worth keeping yet — or export a backup code first).
- If the passphrase is lost or changed, later builds cannot update the installed app: export a backup code, uninstall,
  install the new build, import the code.
- This key is for the development app only. A Google Play release uses a separate **upload key** and Play App Signing;
  set that up when preparing the first release (release-signed AAB, its own secret).

## Developer tools

`DEV_TOOLS` (`src/game.js`) stays `true` on the website as before. The APK packaging flips the one line:
`build-web.js` writes `DEV_TOOLS = false` unless `--dev-tools` is given (only the debug workflow passes it), records the
value in `native/build-info.json`, and `app/build.gradle` refuses any **release** build whose packaged game has
`devTools: true` (verified: `assembleRelease` fails with a dev-tools game and succeeds with a release-safe one). So Custom
encounter, Give items, God Mode, Force CPU and the other developer tools cannot reach a release APK/AAB by accident; the
game logic also refuses each developer action itself when `DEV_TOOLS` is false (`tests/devtest.js`, `tests/god-mode.js`,
and `tests/e2e-android-web.js` on the packaged release configuration, which calls the actions directly).

## Phone: download and install the APK

1. Open **github.com** in Chrome (signed in) → the repository → **Actions** → **Android debug APK** → the newest
   run with a green tick.
2. Open the *Build the debug APK* job summary and tap the **direct link** in "SnapMon Dev APK — download this" (or
   scroll to **Artifacts** → **SnapMon-Dev-APK-…**; never one ending in `UNSTABLE-SIGNING`). A `.zip` downloads.
   **Before installing: make a fresh backup code** (Settings → Back up your progress; `docs/RECOVERY.md` section 2).
3. Open it in **Files** (Downloads) → tap the zip → **Extract** → tap the extracted `snapmon-dev-….apk`.
4. First time only: Android asks to allow installs from this source (Chrome or Files) → **Settings → Allow** → back →
   **Install**. Play Protect may warn about an unknown developer → **More details → Install anyway**.
5. Updating: repeat with a newer run; Android says "Do you want to update this app?" → **Update**. If it says
   "App not installed" / conflicts with an existing package, the signing key differs (see Signing) or the build is
   older than the installed one.

## Phone smoke-test checklist

1. **Starts from zero:** first launch shows a brand-new player (level 1, no monsters, starting coins/items). Your
   Chrome progress is NOT there (expected).
2. **Offline:** turn on Airplane mode before the first hunt; everything below should still work.
3. **Engine:** the Spirit Lens shows loading then "ready" by itself; no download notice. Note how long it takes.
4. **Camera:** SNAP → Android asks for camera permission → **Allow** → rear camera preview; zoom slider/buttons work.
   Also try once **Don't allow**: an explanation appears (pointing to Android settings), no crash.
5. **Recognition:** photograph a few objects; Scan for monsters, Wrong object choices, and the normal identification
   flow behave like the website. Note the time per photo (Settings → developer panel shows timings).
6. **Battle and capture** a monster; check Monsters / encyclopedia.
7. **Save:** note coins/monsters → swipe the app away (or Settings → Apps → Force stop) → reopen → all there.
8. **Background/resume:** press Home during the camera and during a battle; return after a minute → camera closed,
   game intact, SNAP works again after the lens wakes up.
9. **Back:** Back closes sheets/camera, returns to Hunt; on Hunt the first Back shows "Press Back again to exit", the
   second leaves the app; reopen → progress kept.
10. **Update:** install a newer build over it → progress kept. (Uninstall → reinstall should start from zero.)
11. **Website still independent:** open https://patrikarendas-droid.github.io/snapmon/ in Chrome → your old Chrome
    progress is unchanged and the website works as before.
12. Settings shows "Android app … · DEVELOPMENT BUILD"; Open-source licences opens.

Report: phone model + Android version, Android System WebView version (Settings → Apps → Android System WebView),
engine start time, seconds per photo, anything odd.

## One recogniser, bundled in the app

Hybrid recognition (COCO-SSD lite + MobileNet v2 + TinyCLIP ViT-39M/16 with the calibrated decision rules) is part of
the game, not an option. The APK should **contain** every model and runtime file so all players run the same versions
and nothing is fetched from AI hosts during play.

- **One asset base.** All engine files are addressed through `Platform.assets.url(path)`. The web build serves them
  from the site. The native build sets `window.SNAPMON_ASSET_BASE` (e.g. `https://localhost/` for Capacitor's local
  server, which serves the app's `public/` folder) before the scripts load. No other code changes.
- **The file list already exists.** The deploy writes `models/manifest.json` with every file's path, size and SHA-256.
  A native build step can copy exactly those files into the app and verify them. The worker already checks TinyCLIP
  downloads against the manifest.
- **Size.** About 32.6 MB (detector, classifier and TF.js) plus about 53 MB (TinyCLIP 38.8 MB, vocabulary 2.9 MB,
  ONNX Runtime CPU/WASM build 11 MB), roughly 86 MB. Since v0.4.1 the 22 MB WebGPU runtime build is used only by a
  developer comparison switch and need not be bundled in the APK.
  - Google Play's limit for the base download is 200 MB (Android App Bundle), so the models fit. **Play Asset
    Delivery** with an *install-time* asset pack is the alternative if the base module needs to stay small. Install-time
    packs arrive with the app, are updated with each release, and need no in-game download screen.
  - Avoid *on-demand* or *fast-follow* packs for the engine: they reintroduce a "download before you can play" state.
- **Updates.** Model changes ship as normal app releases. Bump `ENGINE_ID` in `src/engine.js` whenever a model file,
  the vocabulary, a threshold or a decision rule changes. Every monster records the engine that identified it
  (`monster.photo.engine`), for future competitive or multiplayer checks.
- **Licences.** All models and runtimes are under permissive licences compatible with commercial distribution (see
  `THIRD_PARTY_NOTICES.md`). The APK must include those notices, e.g. on a Settings → Licences screen.

## Same AI, different hardware

| Part | GPU path | CPU path | Same weights? |
|---|---|---|---|
| Detector + classifier (TF.js) | WebGL | TF.js CPU backend | yes (automatic fallback, also mid-session if WebGL is lost) |
| TinyCLIP (ONNX Runtime Web, in a worker) | developer comparison only (WebGPU) | **standard for every player since v0.4.1**: WebAssembly, one thread | yes |

- If both backends fail, the player gets "SnapMon's recognition engine couldn't run on this device. Please check for
  system updates or try again." with a Retry. Hunting never continues with a weaker model.
- **WebView caveats.**
  - TinyCLIP no longer depends on WebGPU, so WebView's patchy WebGPU support does not matter for it.
  - TinyCLIP is pinned to one WASM thread so every device does the same arithmetic. Multi-threaded WASM (needs
    cross-origin isolation: `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy:
    require-corp`) could be faster, but should only be enabled after checking that it gives identical scores.
- **Consistency.** TinyCLIP on WebGPU changed the outcome on ~4.5% of benchmark photos, which is why it runs on the
  CPU for everyone. Remaining differences (WebGL detector, canvas preprocessing) are listed in `docs/RECOGNITION.md`.

## Camera
- **Web build:** uses `getUserMedia` with the rear camera. It starts only after a tap and stops on capture, on close,
  on Back, or when the app is hidden. There is no gallery and no file input.
- **Capacitor:** the same `getUserMedia` call works in the WebView once the app holds `android.permission.CAMERA` and
  grants the WebView's permission request (Capacitor's bridge does this).
- **Permissions:** CAMERA only. INTERNET is removed from the app (the models are bundled).
- **In the app (v0.6.0 dev APK):** Capacitor's WebChromeClient turns the page's camera request into Android's runtime
  CAMERA permission prompt; if the player refuses (or Android stops asking), the game explains how to allow it in
  Android Settings. Not yet tested on a real phone.
- **Zoom (v0.4.2).** If the camera track reports a `zoom` capability (`MediaStreamTrack.getCapabilities()`), the game
  uses real camera zoom through `applyConstraints({ advanced: [{ zoom }] })`. Chrome on Android supports this on many
  phones, but which phones and which zoom range is up to the phone's camera driver; it has not been checked on a real
  device yet. Otherwise the game uses a digital zoom of up to 3×: the preview is scaled and the photo is cropped to
  exactly the same region. Either way the photo (and what recognition sees) matches the viewfinder. Digital zoom
  lowers the resolution (at 3×, a 1280 px frame leaves about 430 px), which recognition handles because the models work
  at 224–300 px anyway. A native build can use CameraX zoom behind the same `Platform.camera.setZoom`.
- **Viewfinder = photo (v0.4.2).** The viewfinder crops the camera frame to 3:4 (`object-fit: cover`). Before v0.4.2
  the photo contained the full frame, including edges the player could not see; now it is cropped to the visible region.

## A possible iOS version later (notes only; Android comes first)
- Game logic, sprites, saves and the Guide are plain JavaScript with no platform dependency. Device access goes through
  `src/platform.js` (camera, storage, assets), so an iOS shell (e.g. Capacitor) would replace only that layer.
- Recognition runs on TF.js (WebGL or CPU) and ONNX Runtime WebAssembly, both of which work in iOS Safari / WKWebView.
  Because TinyCLIP runs on WASM for everyone (v0.4.1), WebGPU support differences between Android and iOS do not matter.
- The Back-button logic (`window.SnapmonNav.back`) is Android-specific by nature; iOS has no hardware Back, and the
  same screens already have on-screen Close/Back buttons.
- The Long Tasks API used by the developer camera diagnostics does not exist in Safari; the code skips it there.
- No Android-only dependency has been added that would block iOS.

## App lifecycle (background / resume)
- Android Chrome freezes background pages and may drop their GPU context (WebGL) or stop workers to save memory. v0.4.2
  checks the engine when the page becomes visible again (`visibilitychange`, `pageshow`): it detects a lost WebGL
  context (`webglcontextlost`, `isContextLost()`) and pings the TinyCLIP worker, and if anything is broken it reloads
  both parts from the phone's cache (no download). A hunt that fails anyway triggers the same recovery and one retry;
  Try again always reinitialises. Recoveries never switch to another model.
- **Limit:** if Chrome kills the whole page (common after a long time in the background or under memory pressure), it
  reloads from scratch when reopened. Progress is safe (saved before the heavy step and when the app is hidden), but
  nothing in memory can survive that. A native app has the same limit when Android kills its process.
- The camera is always stopped when the app goes to the background; the player reopens it with SNAP.
- **SNAP readiness (v0.4.3).** SNAP is disabled (not just dimmed) while the engine loads, wakes up, re-checks itself
  after a resume or has failed; the camera shutter additionally needs live frames. This also removes the
  frozen/blank viewfinder seen with "Force CPU backend": the CPU detector's start-up blocks the page's main thread for
  about a second, and before v0.4.3 the camera could be opened during exactly that start-up.

## Back button
The game already routes Back through one function:

```js
// Capacitor (@capacitor/app)
import { App } from '@capacitor/app';
App.addListener('backButton', () => {
  if (window.SnapmonNav.back() === 'exit') App.exitApp(); // or App.minimizeApp()
});
```

`SnapmonNav.back()` returns:
- `'handled'`: it closed a sheet, the camera or a screen, or refused to abandon a battle;
- `'armed'`: on the Hunt screen, it showed "Press Back again to exit SnapMon.";
- `'exit'`: the second press within 2 s.

In the browser the same function is driven by a History API guard entry (see `src/ui.js`). Native code gives fully
reliable double-Back, which Chrome cannot guarantee (see the README). **Implemented** in `android-app/native/boot.js`
(Capacitor `App` plugin); on `'exit'` it first waits for pending save writes, then calls `App.exitApp()`.

## Storage
- See "Saves in the Android app" above: localStorage (synchronous) + atomic native files (`SnapmonSaveStore`),
  newest copy wins at start-up; export/import backup codes unchanged.
- Model files in the APK need no browser cache at all (`Platform.assets.bundled`).

## Compatibility testing before a store release (not done yet)

Nothing below has been measured beyond the developer's own phone (WebGPU in Chrome: TinyCLIP ~1.5 s median, ~3 s on
the first photo, no warming over 30 photos).

1. **Devices.** At least:
   - a recent mid-range phone (WebGPU likely);
   - a 3–4-year-old mid-range phone (WebView WebGPU unlikely → WASM);
   - a 3–4 GB RAM phone;
   - an Android Go or very low-memory device to find the floor.
2. **Measure on each:**
   - engine initialisation time;
   - first and repeated photo times;
   - which backends ran (Field-test log);
   - peak memory (Android Studio profiler or `adb shell dumpsys meminfo`);
   - WebView crashes or renderer kills over 50 photos;
   - temperature and battery.
3. **Set the minimum from data:**
   - Candidate rule: Android version with a WebView that runs WASM SIMD (Android 8+ with an updated WebView) **and** a
     minimum RAM where 50 consecutive photos complete without the renderer being killed.
   - Do not exclude devices only for lacking WebGPU: the CPU path runs the same engine.
4. **Play Console.** Use the Device Catalog to exclude genuinely incompatible devices (by RAM or SoC) once the floor
   is known. Declare the camera as a required feature.

Known risks:
- Memory pressure on 2–3 GB phones while both model parts are resident (~100 MB of weights plus runtime buffers).
- Very slow WASM on old CPUs: recognition times out after 45 s with a message.
- **Seen on the CI emulator (software GPU, SwiftShader):** the first engine start with TF.js on WebGL took > 3 min and
  Android showed "SnapMon Dev isn't responding" (shader compilation blocks the page's main thread; the detector hit its
  180 s timeout). Real phones have a hardware GPU, but on the phone test watch the first engine start after install:
  time it, and note any "isn't responding" dialog. The emulator test therefore runs the detector on the CPU backend.
- WebView builds without SIMD.
- Background eviction of a browser cache: this only affects the web version.
